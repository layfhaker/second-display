# Дорожная карта (по факту)

Статус на 2026-06-24. Каждая фаза — самостоятельно проверяемый результат.

## Фаза 0 — Тулчейн ✅
- .NET 8 SDK, Android Studio (+adb), EWDK (для драйвера). **Без Visual Studio.**
- Проверки: `dotnet --list-sdks`, `adb version`. См. `docs/PREREQUISITES.md`.

## Фаза 1 — Картинка на планшете ✅
- Host: захват экрана (GDI) → изначально JPEG, **сейчас HEVC** (QuickSync/Media Foundation).
- Транспорт: TCP 27315 + `adb reverse`.
- Android: TCP-клиент → `MediaCodec` → `SurfaceView`.
- Результат: видео идёт ~25-30 fps, картинка резкая, курсор виден.

## Фаза 2 — Тач как мышь ✅
- Клиент шлёт TOUCH, host инъектит `SendInput` (абсолютные координаты).
- Результат: тап/проводка по планшету двигает курсор и кликает на ПК.

## HEVC + полировка ✅ (вместо изначального JPEG/H.264)
- Перешли с JPEG на аппаратный HEVC (Media Foundation MFT → QuickSync), всё в нашем коде
  через `Vortice.MediaFoundation`, без ffmpeg.
- Дорисовка курсора, DPI-awareness, letterbox с правильным маппингом тача.

## Фаза 3 — Виртуальный дисплей (расширение) ✅ РЕШЕНО (2026-06-25)
Цель достигнута: настоящий 2-й монитор, нативное 4К, поток на планшет.

  root-устройстве без ресурсов (для этого и сделан IddCx).
- **3.✅ РЕШЕНИЕ — готовый драйвер.** Поставили **VirtualDrivers/Virtual-Display-Driver (MttVDD)**,
  официальный `setup-x64.exe` (драйвер подписан SignPath→GlobalSign, обёртка-инсталлятор без подписи).
  `UmdfLibraryVersion=2.25.0 + UmdfExtensions=IddCx0102`, hwid `Root\MttVDD`. Встал на ХОСТ,
  `Status=OK` — виртуальный дисплей работает. Доказывает: IddCx исправен, наш драйвер падал ТОЛЬКО

- **3.✅ Захват + поток.** Хост наводится на виртуальный дисплей (`--display <idx>`), захват через

  0 discard.** GDI давал лишь 7 fps и из-за медленной подачи вешал энкодер (чёрный экран) — DXGI
  починил и fps, и это.
- **3.C Железо (CM489) — отклонено** пользователем (ненадёжно/забывается). Больше не нужно.

## Фаза 4 — GPU zero-copy: пробить 50→60→144 fps + срезать задержку ✅ ОСНОВНОЕ СДЕЛАНО (2026-06-26)
**Был корень потолка fps и задержки:** кадр шёл **GPU(DXGI-захват) → CPU(staging-копия
+ наложение курсора + `BgraToNv12`, ~25мс/кадр) → GPU(QuickSync-энкодер)** — крюк через CPU с двумя
пересылками GPU↔CPU. Теперь **весь тракт в видеопамяти, без CPU**:
- **✅ Риск-звено проверено первым (`--probe-d3d11`):** QuickSync-MFT на Iris Xe **принимает
  D3D11-вход** — `MF_SA_D3D11_AWARE=1`, `SET_D3D_MANAGER` OK, ProcessInput жрёт NV12-текстуры,
  закодировал 10 кадров. Зелёный свет на zero-copy.
- **✅ BGRA→NV12 на GPU через `ID3D11VideoProcessor`** (`host/GpuColorConverter.cs`): аппаратный VPP-блок
  iGPU, без шейдеров. Цветовое пространство BT.601 studio (как в старом CPU-коде) → цвета совпадают.
- **✅ Zero-copy в энкодер** (`host/HevcEncoder.cs`, режим D3D11): NV12 отдаётся MF-энкодеру прямо
  как **D3D11-текстура** через `MFCreateDXGISurfaceBuffer` + общий `IMFDXGIDeviceManager`/девайс
  между захватом и MFT. Кольцо из 4 NV12-текстур, без копий через RAM.
- **✅ DXGI-захват остаётся на GPU** (`DxgiCapture.UpdateGpu`): `CopyResource` GPU→GPU, без readback.
- **Проверено end-to-end headless** (`--selftest-gpu`): реальный монитор → VPP → энкодер → валидный
  декодируемый HEVC, цвета верные (ffmpeg-декод кадра подтверждён). 161 кадр, всё через GPU.
- Включается по умолчанию (есть `--cpu` для отката на старый путь). Курсор на GPU: VPP отвергает
  substream-текстуру курсора (`E_INVALIDARG` на мелкой текстуре) → **graceful degradation**, поток
  идёт без курсора. Чистый путь курсора — рисовать на планшете (см. идею ниже), отложено.

**Замерено на планшете (2026-06-27, VDD 3392×2400 = 8.1 Мпикс, GPU-режим):**
- ✅ **Задержка ушла** — пользователь подтвердил, лага больше нет (это была главная жалоба).
- ✅ **Захват ускорился:** ~30 → **47 fps** (GPU, без CPU-readback).
- ⚠️ **Кодирование ПРОСЕЛО: ~30 → ~16 fps** (encoded+sent). Захват растёт 33→47, кодек падает 26→16.
  Регресс на полном 8.1 Мпикс — **нужно поднять fps кодирования.**

### Прочие идеи производительности (после GPU-конвейера)
- **Zero-copy в энкодер:** отдавать MF-энкодеру кадр прямо как **D3D11-текстуру** (`MF_SA_D3D11_AWARE`,
  hardware sample) вместо CPU-NV12 → захват→кодек без копий через RAM. Это и есть «свой путь» к
  потолку железа (цель 60, затем 120/144 — VDD под 144 Гц config поддерживает).
- **Dirty-rects:** Desktop Duplication отдаёт изменённые прямоугольники — кодировать/слать только их
  на статике → меньше CPU и трафика.
- **Курсор отдельным слоем:** слать позицию+форму, рисовать на планшете локально (нулевая задержка
  курсора) — альтернатива композиту на хосте, разгружает конвейер.
- Динамический битрейт, запрос IDR при потере пакета.
- (Опц.) интегрированный захват из самого драйвера (shared memory) — но с DXGI уже не обязательно.

## Фаза 2.6 — Клавиатура и горячие клавиши с планшета ✅ (2026-06-26)
Цель: подключённая к планшету клавиатура (BT/USB) или экранная клавиатура работает как ввод на ПК.
- ✅ **Android:** перехват `KeyEvent` (физ. и экранная клавиатура) → новый тип пакета `KEY` в протоколе
  (keycode, action down/up, modifiers: ctrl/alt/shift/meta).
- ✅ **Host:** инъекция через `SendInput` (`KEYBDINPUT`). Маппинг Android
  `KeyEvent.KEYCODE_*` → Windows virtual-key / scan-code.
- ✅ **Горячие клавиши:** Ctrl+C/V/Z/X, Alt+Tab, Win+D и т.д. — передаются как комбинации modifier+key.
  Возможна будущая панель быстрых хоткеев на планшете (overlay с кнопками Ctrl+Z, Alt+Tab и пр.).
- ✅ **Важно:** `dispatchKeyEvent` на Android перехватывает ДО системной обработки → клавиатурный ввод
  не «застревает» в Android-приложении.
